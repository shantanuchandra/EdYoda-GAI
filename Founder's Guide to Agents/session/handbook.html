This handbook carries the two live builds, reusable prompts, safety boundaries, and the operating notes that make the workshop run.

02 / Build

Build 01

Weekly Repo/Product Digest

Read recent commits, translate them into ordinary language, and deliver a useful summary. The goal is not a prettier git log—it is a shipping narrative.

01

Give Hermes repository access

Use a fine-grained GitHub token limited to the selected repository, with read-only Contents and Metadata. Add it to ~/.hermes/.env as GITHUB_TOKEN.

02

Validate live data

Ask for the last seven days of commits. Confirm the response includes real commit data before you ask for a summary.

Look at the last 7 days of commits on <github-owner/repository>. List what changed, including the real commit messages and relevant files.
03

Write the digest

Using the commit data you just read, write a 3–5 sentence summary of what shipped this week for a non-technical co-founder. No git jargon. Group related commits into one product story. Explain why the change matters where the commit data supports it.
04

Optional: make it recurring

Only after the digest works manually, ask Hermes to schedule the weekly summary. Confirm the exact scheduling mechanism on the current Hermes build first.

03 / Build

Build 02

Investor Qualification + Outreach

Start with an honest description of your round, research fit, score it, then create Gmail drafts. Drafts are reviewable; they are never auto-sent.

01

Test Gmail with a safe draft

Create a Gmail draft addressed to me. Subject: Hermes test. Body: This is a test draft. Do not send it.
02

Describe your round

I am raising a <stage> round in <sector>, based in <geography>, looking for <check size> checks. Other context that matters: <notes>.
03

Research and score fit

Search for 5–8 currently active investors that fit my stage, sector, geography, and approximate check size. For each, give the source link, evidence for the fit, and a 1–3 fit score. Flag uncertainty instead of making it up.
04

Draft, do not send

For <investor/fund>, draft a personalised outreach email under 150 words. Reference one specific, sourced reason they fit my round. Create it as a Gmail draft only. Do not send it.

06 / Recover

Troubleshooting

Check the boundary that failed.

Hermes does not respond
Confirm hermes gateway is still running and that hermes status reports the intended provider and model.
Tool or skill is missing after adding a token
Restart Hermes or run /reload-mcp inside chat. Then perform a small read-only tool check before attempting the full workflow.
GitHub, Gmail, or the action step fails
Check permissions and token scope first. Most build failures are data-source or authorisation failures, not reasoning failures.
SSL certificate verification fails
Do not disable certificate verification. A managed network may be inspecting HTTPS traffic; use an unrestricted connection or follow your organisation’s approved CA-certificate process.

Facilitator operations

Keep the build moving, not merely the room quiet.

Before the room

Dry-run both recipes. Confirm Hermes, direct OpenAI access, Telegram, GitHub read access, Gmail draft creation, and the fallback repo/list.

During Build 01

Ask founders to validate real commit data before asking for prose. If a repo is quiet, switch to the shared fallback repository immediately.

During Build 02

Test Gmail draft creation first. If live investor research is thin, switch to the curated list; never present a generic answer as sourced research.

If time is tight

Protect the two done states: a real digest and an unsent Gmail draft. Defer scheduling and extra iterations.

If a demo fails

Name the failure honestly, use the prepared fallback, and preserve the live-data → reasoning → action lesson. Do not troubleshoot silently for ten minutes.

Close strong

Have each founder state the next agent they would sketch. The goal is a working pattern, not a perfect automation.
