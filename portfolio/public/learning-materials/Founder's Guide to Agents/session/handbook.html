01 / Decide

The agent test

Know what you are building.

A prompt can be useful. An agent becomes useful on its own terms when it gets fresh information, changes something outside the chat, and can run again without you recreating the request.

Live dataIt pulls a repository, web result, inbox, or other system you did not paste in.
External actionIt writes, updates, drafts, or notifies somewhere beyond the chat.
TriggerIt can run from a schedule, webhook, or event—not only from a fresh manual prompt.

Before you begin

Choose one repository with commits from the last seven days. If your repo is quiet, use the facilitator’s fallback repo; this is a rehearsal of the pattern, not a score of your velocity.

01

Create least-privilege access

In GitHub, create a fine-grained personal access token limited to the repository you selected. Grant read-only Contents and Metadata. Save it in ~/.hermes/.env as GITHUB_TOKEN, then restart Hermes if it is already open.

Do not paste the token into a chat. The only place it belongs is your local Hermes environment file.
02

Check that the repository is reachable

Ask for raw recent activity first. A generic answer is not success—look for real commit messages, dates, or changed files.

Look at the last 7 days of commits on <github-owner/repository>. Return the commit date, commit message, and a short description of the files or area changed for each item.
03

Turn the activity into a product digest

Only after Step 2 works, send the transformation prompt. If it reads like a changelog, change the audience and ask for a rewrite.

Using only the repository activity you just retrieved, write a 3–5 sentence weekly product digest for a non-technical co-founder. Group related commits into one story. Explain what changed and why it matters when the evidence supports it. No git jargon, no invented outcomes.
Rewrite the digest for <investors / customers / internal team>. Keep it under <number> words. Remove implementation detail and retain only evidence-supported product impact.
04

Make the delivery repeatable (stretch)

Once the manual run works, ask Hermes how its current scheduler is configured and create a weekly Monday 9am job. Verify the schedule in Hermes before relying on it.

Show me the supported way to schedule a weekly task in this Hermes installation. If scheduling is available, create a Monday 9am task that reads the previous 7 days of commits for <repo>, writes the approved digest format, and delivers it here. Confirm the schedule after creating it.
03 / Build

Build 02 · Investor Qualification + Outreach

Research fit, then create drafts for review.

Your done state: at least one evidence-backed fit score and one personalised unsent Gmail draft. The founder remains the decision-maker at every step. Two agents run in sequence: Pragya (प्रज्ञा, intelligence) handles search and scoring; Varta (वार्ता, communication) drafts and saves.

Clarify is a feature, not a stall

Live-tested on 2026-07-18: a real Telegram run for a pre-launch app paused at the Clarify node and asked for monthly visitors, conversions, revenue, and incorporation status before drafting anything. It explicitly offered to "present it honestly" if the numbers were zero. This is the pipeline doing its job — asking a relevant question beats fabricating a number. Answer in one message with real figures (or "pre-launch / zero" where true) and the run resumes automatically from where it paused.

Live-tested: the trigger reaches more than Pragya→Varta

Same test run, 2026-07-18: after scoring investors, Hermes offered a 4-option menu — three were outreach batches, the fourth was "turn the deck outline into a polished investor deck first." Choosing it produced a real 10-slide .pptx delivered as a Telegram file attachment, built only from the verified beta metrics supplied earlier (no invented traction). SOUL.md's Pragya→Varta block does not mention deck generation — this confirms the short-command trigger is an entry point into a broader fundraising capability, not a narrowly-scoped pipeline. Worth deciding deliberately whether to document deck-build as a third named stage or keep it as an undocumented adjacent skill.

Live-tested: "submit priority 1" reached for the wrong email tool

Same session, continuing from the deck path: the founder replied "submit priority 1" to send the deck to First Cheque, Titan Capital, India Quotient, and Indian Angel Network. First Cheque and IAN correctly blocked on a web-form requirement (no email applicable there). But for Titan Capital and India Quotient — both email-reachable — Hermes reached for the Himalaya email skill instead of the pipeline's own gmail_draft_standalone.py, found Himalaya unconfigured, and reported "no email client configured" even though Gmail OAuth was already working. Root cause: the "submit/apply" request never went through the Pragya→Varta trigger, so it had no standing instructions telling it which email tool to use — it improvised and picked wrong.

Fix applied — SOUL.md now covers submit/apply for any trigger

Added a new SOUL.md block that applies regardless of how the request arrives (short-command trigger, deck-review follow-up, or ad-hoc): investor email always goes through gmail_draft_standalone.py, Himalaya is explicitly forbidden for outreach, and "only Himalaya looks available" must be treated as "no email tool available" — never a silent fallback. Mixed batches (some investors need email, others need a form) now split correctly instead of blocking the whole batch. Restart Hermes after editing SOUL.md for the fix to take effect.

Before you begin

This build has a one-time setup cost the digest agent didn't: Google OAuth. Steps 1–2 are setup-only; they do not need repeating once done. Do not jump to the search prompts until the test draft (Step 2) is confirmed in Gmail Drafts. Skipping ahead is the single most common cause of workshop time loss.

01

Set up Google OAuth — every click, in order

A. Create OAuth credentials in Google Cloud Console

Open console.cloud.google.com. Select or create a project (name does not matter). Then:

  • Left sidebar → APIs & Services → Library → search Gmail API → click the Gmail API result → click Enable.
  • Left sidebar → APIs & Services → OAuth consent screen → choose External → fill App name (anything) → Save. Then click Test users → Add users → enter the Gmail address you will authenticate with → Save.
  • Left sidebar → APIs & Services → Credentials → Create Credentials → OAuth client ID → Application type: Desktop app → Create → Download JSON.

Move the downloaded file to ~/.hermes/google_client_secret.json. In Terminal:

mv ~/Downloads/client_secret_*.json ~/.hermes/google_client_secret.json

Verify it landed:

ls -lh ~/.hermes/google_client_secret.json

Expected output: a line showing the file, roughly 400–500 bytes, dated today. If you see No such file or directory, check the filename — Google sometimes saves it with a long numeric prefix.

B. Run the OAuth flow

cd ~/.hermes/hermes-agent/skills/productivity/google-workspace/scripts python3 setup.py --client-secret ~/.hermes/google_client_secret.json

Expected output: a URL starting with https://accounts.google.com/o/oauth2/auth?... printed to the terminal, then a prompt waiting for input.

Copy that entire URL, paste it into a browser, sign in with the Gmail address you added as a test user, click Allow. The browser shows a code — copy it. Return to Terminal immediately and paste:

python3 setup.py --auth-code <paste-code-here>

Expected output: Token saved or similar confirmation line. If you see invalid_grant or Token has been expired, the code expired — re-run the setup line to get a fresh URL and complete the browser flow within 5 minutes.

C. Verify the scope

python3 setup.py --check

Expected output: AUTHENTICATED and a list of scopes. Look for gmail.modify in that list.

Scope check — do not skip. You need gmail.modify, not gmail.compose. gmail.compose includes "send emails" capability — wrong for a draft-only pipeline. If gmail.compose appears instead, do not use setup.py for this build. Use the standalone script in your Hermes Build Recipe Part 2 appendix (gmail_draft_standalone.py), which explicitly requests gmail.modify and stores its token separately at ~/.hermes/gmail_modify_token.json.
02

Prove the action boundary with a test draft

Hermes's built-in Google tools cover send and read, not create-draft. The helper script handles drafts. Run this exact command — replace your.email@gmail.com with the Gmail address you authenticated with:

python3 ~/.hermes/scripts/gmail_draft_standalone.py \ --to your.email@gmail.com \ --subject "Hermes test draft" \ --body "This confirms Gmail draft creation is working. Do not send."

Expected output in the terminal: a JSON object containing a draft_id field — something like {"id": "r-55083932...", "message": {...}}. That ID confirms the draft was created.

Then open Gmail in a browser. Go to Drafts (left sidebar). You should see a message with subject "Hermes test draft". If it's in Sent instead — stop. Something called a send endpoint instead of the draft endpoint. Re-check the script source.

If you see a Python error instead of JSON, common causes:

  • FileNotFoundError: google_client_secret.json — file not at ~/.hermes/google_client_secret.json. Re-check Step 1A.
  • HttpError 403 — Gmail API not enabled. Go back to Cloud Console → APIs & Services → Library → enable Gmail API.
  • Token file not found — auth flow not completed. Re-run Step 1B.
03

Trigger Pragya — two ways

Once setup is confirmed, you trigger the Pragya → Varta pipeline in whichever way fits your workflow.

Option A — Short Telegram command (fastest)

Send this to your Hermes Telegram bot. Replace the bracketed values with your actual details:

get my <app-name> app a <stage> investor from <region> region with checks around <check-size>

Real examples:

get my CardCompass app a pre-seed investor from Dubai region with checks around $500K
get my Buildwise app a seed investor from India region with checks around $1M–$2M
get my FleetOps app a Series A investor from Southeast Asia region with checks around $3M

Hermes extracts four parameters from that one line — app name, stage, region, check size — and immediately runs Pragya's two-pass search without asking for more information. The app name is used in both the search query and the outreach draft subject line.

Expected reply from Hermes on Telegram within 2–3 minutes: a message naming the top matches with scores, and confirming how many drafts were saved to Gmail Drafts.

Option B — Long-form chat (more control)

Paste this into the Hermes chat window, then follow Steps 4–6 manually for search, scoring, and draft:

I am raising a <stage> round for <app-name>, which operates in <sector>. We are based in <geography> and looking for approximately <check size> checks. Context that matters: <traction, business model, thesis, or restrictions>.
04

Pragya — run two searches, not one

A single broad query consistently returns the same 5–6 widely-covered names. Run both prompts before moving to scoring. Do not score after only one search.

Search for active <stage> investors in <sector> investing in <geography>-based startups, check sizes around <target>. List 5–8 real, currently active funds. For each: name, a direct source link (fund website or dated press article — not a Crunchbase or Tracxn listicle), check size, stage focus, geography. Exclude any result without a direct source link.
Now search again with a recency filter: funds that made investments in <sector> in the last 12 months, or announced a new fund targeting <geography> in the last 18 months. Add any new names not already on your list. Same format — name, direct source link, check size, stage, geography.

After both searches complete: ask Hermes to deduplicate and give you the full combined list before proceeding.

If the response links to aggregators only, or gives vague dates like "active investor" without a citation — stop and use the fallback investor list in the next section of this handbook as your input data.

05

Pragya — score each criterion separately

Separate scoring prevents a strong stage fit from masking a geography dealbreaker. Each criterion is rated before the overall.

For each investor on the combined list, score these four criteria independently as HIGH / MED / LOW / UNKNOWN, then give an overall fit rating (1 weak · 2 moderate · 3 strong): 1. Stage fit — does their typical stage match <my stage>? 2. Sector fit — active portfolio evidence in my sector? 3. Geography — invest in <geography>-based companies without requiring a flip? 4. Check size — my target check <check size> within their stated range? Cite the specific source evidence for each criterion. Mark UNKNOWN if evidence is missing — do not guess.

Expected output: a table or list with all four criteria rated for each investor, plus a score 1–3. Review the scores before moving to drafts. Pass only investors with overall score 3, or score 2 with no LOW on Stage or Geography, to Varta. Discard the rest — do not draft speculative outreach for weak matches.

If any investor has UNKNOWN on Stage or Geography — ask Hermes to do a targeted search for that investor specifically before accepting an overall score. Those two criteria are dealbreakers and should not stay UNKNOWN.

06

Varta — draft and save, never send

Varta drafts only for investors who passed the scoring threshold. The email opens with one specific sourced fact — not a generic sector claim. Under 150 words. Single ask.

For <investor/fund name>, draft an outreach email for <app-name> under 150 words. Requirements: open with one specific sourced fact about this investor (name a portfolio company, a deal they recently made, or quote their exact thesis statement — not a generic claim like "you invest in fintech"); state my round in one sentence (<app-name> is <one-line description> — we are raising a <stage> round, targeting <check size> checks); single ask — a 20-minute call. No "I hope this finds you well," no superlatives. Save it as a Gmail draft. Do not send it. After saving, confirm the draft ID and tell me one specific thing I should verify before sending.

Expected output: the draft text, a confirmation that it was saved (Varta runs gmail_draft_standalone.py), a draft ID, and one concrete verification item (e.g. "Confirm their Fund III is still deploying — last press was Oct 2024").

Open Gmail Drafts to confirm it is there. The draft recipient should be a placeholder — your own email — until you manually add the investor's real address before sending.

NEVER send from here. Drafts go to your Gmail Drafts folder. You read, edit, and send manually. Hermes does not and cannot send from this pipeline — that boundary is deliberate.

08 / Fix

Rate-limit RCA + fixes

Why quota errors happen and how to resolve them permanently.

Three independent root causes compound during a Pragya+Varta run. Each must be fixed separately — fixing one may still leave the other two active.

Root cause 1 — Tier-restricted model

The default Hermes config uses gpt-5.6-sol. This model is Tier 4/5 restricted on OpenAI. Having credits on your account does not give tier access — tier access comes from account age and cumulative spend history, not balance. A new account with $100 loaded is still Tier 1.

The error reads: "You exceeded your current quota" or "No response from provider for 90s (non-streaming, model: gpt-5.6-sol)".

Fix 1 — Keep gpt-5.6-sol; add gpt-5.5 as the rate-limit fallback

Do not change the default model. Instead, add a fallback that Hermes uses automatically when the primary hits a quota error:

nano ~/.hermes/config.yaml
model: default: gpt-5.6-sol fallback: gpt-5.5 fallback_on_errors: - rate_limit_exceeded - quota_exceeded - provider_timeout

Save and restart Hermes. With this in place, every call tries gpt-5.6-sol first. On a quota or timeout error, Hermes retries the same call on gpt-5.5 automatically — you stay on the better model unless the tier wall forces a switch. Once your OpenAI account reaches Tier 4 reliably, you can remove the fallback lines.

Root cause 2 — Aggressive context compression

The default compression threshold is 0.5, which fires at 50% context fill. Compression uses the same model, so it makes a second simultaneous API call mid-conversation — doubling rate-limit pressure exactly when Pragya is running a multi-step search. This is the mechanism that turns a single near-limit event into a hard abort.

Fix 2 — Raise the compression threshold

In the same ~/.hermes/config.yaml:

# Change this line: compression: threshold: 0.5 # To this: compression: threshold: 0.85

This delays compression until 85% context fill. For a Pragya run (~15–20 turns) compression will no longer fire mid-flow.

Root cause 3 — Missing SOUL.md pipeline block

The standing instructions in ~/.hermes/SOUL.md should contain a Pragya→Varta block that tells Hermes exactly what to do when asked to research investors. Without it, Hermes improvises: it asks follow-up questions about traction, incorporation, and founder details, burning through context in multiple turns instead of one structured pass. This causes compression to fire earlier, compounding Root Cause 2.

Check your current SOUL.md:

cat ~/.hermes/SOUL.md | grep -i "pragya\|varta\|investor"

If this returns nothing, the pipeline block is missing.

Fix 3 — Add the pipeline block to SOUL.md

Open the Hermes Build Recipes doc (session folder → 03_Hermes_Build_Recipes.md). Find the block under Part 2, Section 4: SOUL.md update. Copy the full block and append it to your SOUL.md:

nano ~/.hermes/SOUL.md

Paste the block at the end of the file. It should begin with a heading like ## Investor Research (Pragya → Varta) and contain the full structured pipeline instructions. Save. Restart Hermes.

With the block in place, Hermes runs the full pipeline in one structured pass without iterative questioning — reducing total turns by ~60% and eliminating the early compression trigger.

Apply all three fixes, not just one. Root Cause 1 (wrong model tier) is the primary cause. Root Cause 2 (compression timing) turns near-misses into hard aborts. Root Cause 3 (missing SOUL.md block) makes conversations longer than they need to be, increasing exposure to both. Fix them in order: model → compression threshold → SOUL.md.
09 / Recover

Recovery guide

Find the broken boundary.

Hermes is not responding
Confirm the gateway is still running and check hermes status for the selected provider and model.
The repo response is generic
Return to Digest Step 2. Check the repository name, token scope, and whether the response contains real commit data before asking for a summary.
Gmail did not create a draft
Stop before research — don't assume a successful-looking response means the draft actually landed. Match the exact error: "Access blocked … has not completed verification" means your email is missing from OAuth consent screen → Test users. HttpError 403 — Gmail API has not been used means the API itself isn't enabled in APIs & Services → Library. setup.py --check returning NOT AUTHENTICATED means re-run setup.py --client-secret for a fresh auth URL — the auth session expires in ~5 minutes, so complete the browser flow promptly. Then repeat the Step 2 test-draft command and confirm it in Gmail Drafts.
SSL certificate verification fails
Do not disable certificate verification. This commonly points to a managed network inspecting HTTPS; use an unrestricted network or follow your organisation’s approved CA-certificate process.
